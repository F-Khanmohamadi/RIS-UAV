# Joint RIS Placement and UAV Mission Planning for Energy-Efficient Logistics-Assisted Cellular Offloading

Implementation, trained models and raw results of the paper

A rotary-wing UAV delivers a parcel and, on its way, collects the excess uplink traffic of congested cells. Each cell
can be assisted by a reconfigurable intelligent surface (RIS), mounted either on a building facade or on a parked
ground vehicle (ground-mobile RIS). The planner selects the RIS site and the hovering point of every cell, groups
cells that share a hovering point, and orders the stops, so that the UAV energy is minimized under reliability
(packet reception ratio), battery, and deadline constraints. The channel model includes the reflections of all
deployed panels.

This repository contains the code that produced every result in Section V of the paper, the six trained policies, the
raw evaluation records, and scripts that regenerate all figures, tables and numbers quoted in the text.

---

## 1. Methods

All four methods use the same planner. They differ only in how the RIS sites are chosen.

| Method (paper) | Key | RIS sites | Planner |
|---|---|---|---|
| **Route-aware RIS (proposed)** | `proposed` | chosen jointly with the hovering points and the grouping (a cell may also be served without RIS) | trained attention policy (greedy decoding) → repair → iterative local search (100 iterations, full multi-RIS model) → TSP ordering (LKH) |
| Coverage-based RIS | `coverage` | maximize the reliable hovering coverage $\sum_i \lvert\mathcal N_i(\mathbf r)\rvert/\lvert\mathcal Q_i\rvert$ under the multi-RIS model (coordinate ascent from the largest-coverage site of each cell, at most two passes) | same planner, sites fixed |
| Random RIS | `random` | one site per cell, drawn uniformly from the candidates with at least one reliable hovering point | same planner, sites fixed |
| No RIS | `none` | none (direct links only) | same planner |

Implementation: `risuav/sim/eval_rx.py` (methods and evaluation), `risuav/sim/plan_mr.py` (decoding, repair, local
search, TSP), `risuav/sim/model_rx.py` (policy), `risuav/sim/train_rx.py` (training).

## 2. Main results

Final evaluation: 120 test missions per platform on two unseen city layouts, three training seeds (360 mission–seed
pairs per method). All plans are feasible. Mean UAV energy (kJ):

| Method | Facade RIS | Ground-mobile RIS |
|---|---|---|
| No RIS | 101.06 | 101.32 |
| Random RIS | 97.35 | 96.44 |
| Coverage-based RIS | 95.11 | 94.68 |
| **Proposed** | **90.72** | **90.14** |

The proposed method saves 10.2% (Facade) and 11.0% (Ground-mobile) compared with No RIS, with lower energy in every
mission, and 4.6% and 4.8% compared with Coverage-based RIS (lower energy in 93.1% and 94.2% of the mission–seed
pairs). These values are regenerated by `python -m risuav figures` (Section 4) from the files in `artifacts/`.

## 4. Installation

Requirements: Python **3.13** (64-bit), 8 GB RAM, about 1 GB of disk for the quick test and 3 GB for the service
tables of the full study. Windows, Linux and macOS are supported. A GPU is optional (training only).

```bash
python3.13 -m venv .venv
source .venv/bin/activate                    # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
python -m risuav check                       # every package must show "ok"
```

GPU training: install the CUDA build of `torch==2.15.0` from [pytorch.org](https://pytorch.org/get-started/locally/)
before `requirements.txt`. Only the policy network runs on the GPU; GPU runs are reproducible on the same GPU but
not bit-identical to CPU runs. The published checkpoints were trained on the CPU.

VS Code: open the folder, select the `.venv` interpreter, and use the entries of the *Run and Debug* panel, which
call the same commands.

## 5. Reproducing the paper

Every step is one command run from the repository folder: `python -m risuav <command>`. Add `-h` for the options and
`--dry-run` to list the jobs without running them. Every command can be interrupted and re-run; finished work is kept.

### 5.1 From the published results (minutes)

```bash
python -m risuav quick                                  # end-to-end check (about 15 min)
python -m risuav tables --cities city21 gcity21 city22 gcity22   # tables of the test layouts (7-12 min each)
python -m risuav figures                                # all figures, tables and in-text numbers -> outputs/figures/
python -m risuav verify                                 # re-simulate published missions and compare
```

`figures` works without the tables, except for the 3D trajectory figures and the geometric values in
`text_numbers.md` (distances, panel orientation), which need the tables of the test layouts.

## 6. Experimental settings and seeds

All parameters of the system model are in `risuav/sim/physics.py` (`REF`); the experiment settings are in `configs/`.

- **Layouts:** cities 11-14 for training, cities 21 and 22 for testing (unseen). Facade and ground-mobile layouts with
  the same number share buildings, cells, GUEs and missions, so the platform comparison is paired.
- **Training:** 50 epochs × 10 updates × 64 missions, REINFORCE with a greedy rollout baseline (replaced after a
  one-sided paired t-test, α = 0.05, on 200 fixed validation missions), Adam (3·10⁻⁴), StepLR(100, 0.99), gradient
  clipping 1.0, seeds 0, 1, 2. The checkpoint with the lowest validation energy of each seed is used for testing.
- **Test:** missions k = 0-59 of each test layout (120 per platform), `N_ILS = 100`, full multi-RIS model.
- **Random streams:** missions are generated from the layout name and the mission index; the evaluation uses one
  generator per (seed, mission, method), so results do not depend on the method order, on interruptions or on the
  number of parallel workers.
- **Statistics:** mean over missions and seeds; paired savings with bootstrap 95% confidence intervals over
  seed-averaged missions, win rates over the 360 mission–seed pairs, Wilcoxon signed-rank tests with Holm correction.
- **Sensitivity:** N ∈ {16², 24², **32²**, 40²}, D_k ∈ {10, 20, **40**, 80} Mbit (reference in bold), one at a time,
  seed-0 policy trained at the reference values (no retraining), missions k = 0-19 of both test layouts
  (40 per platform). `python -m risuav sensitivity --retrain` additionally retrains at N = 16² and D_k = 80 Mbit; these
  runs are not reported in the paper.

## 7. Implementation notes

These details matter for comparing the code with the paper.

- **Training channel model.** During training, the service of each cell is evaluated with its serving RIS only
  (`"train_model": "serving"`); all test results use the full multi-RIS model. In the final
  test plans, the reflections of non-serving panels change the mean SNR by at most 0.013 dB (`text_numbers.md`,
  Section V-A). `TRAIN_MODEL=coupled` trains with the full model.
- **Local search.** Each of the `N_ILS` iterations selects a random cell and evaluates, for every allowed RIS option,
  the best *relocation* (new hovering point) and the best *merge* (joining an existing hovering point). The route change
  is estimated by the insertion cost, other cells affected by a site change are re-evaluated under the new placement,
  and the move with the largest energy decrease is applied if it decreases the energy and keeps all cells feasible.
  For the benchmarks, the RIS option of each cell is fixed.
- **Visiting order.** After the local search, the stops and the parcel destination are ordered by the
  Lin–Kernighan–Helsgaun heuristic (`elkai`).
- **Validation and checkpoints.** The validation energy is that of the greedy policy without local search; it is
  therefore higher than the test energies.

`docs/IMPLEMENTATION_DECISIONS.md` lists every implementation decision and the test that checks it.

## 8. Verification status

Checked on 18 Nov 2026 by extracting this repository into an empty folder and installing `requirements.txt` in a new
virtual environment (Linux, CPU, Python 3.13); details in `docs/TEST_REPORT.md`.

- All documented commands run without error (`check`, `test`, `quick`, `tables`, `figures`, `verify`, a short
  `sensitivity` run, and the dry runs of `train`, `evaluate`, `sensitivity --retrain` and `reproduce`).
- `figures` regenerates all tables and statistics byte-identically to the values reported in the paper.
- `verify` re-simulates published missions with the published checkpoints; plans and energies are identical.
- Service tables built in the clean environment are bit-identical to those of the reported runs.

Not verified here:

- **Full retraining** (6 × 50 epochs) and the **full evaluation** through this interface were not repeated after
  packaging; they use the same scripts as the reported runs. Training resumes correctly after interruption, and the
  initial validation energy of a new run equals that of the reported run.
- **Windows and GPU** runs (wheels exist for every pinned package; the code builds all paths with `os.path`).
- On other systems, other builds of the numerical libraries can flip a discrete choice (a CQI level or a local-search
  move) in single missions; `verify` reports the largest difference. Averages over 360 mission–seed pairs should agree
  within the reported confidence intervals.
- The Excel charts were checked in LibreOffice, not in Microsoft Excel.
- Figure fonts: the scripts use STIXGeneral (bundled with matplotlib) so that figures look the same on every system;
  the figure data are identical to those in the paper.

## 9. Troubleshooting

| Problem | Fix |
|---|---|
| `No module named risuav` | Run the command from the repository folder. |
| A package shows `differs` in `check` | `pip install -r requirements.txt` inside the activated environment. |
| `missing table ...` | `python -m risuav tables --cities city21` (or `--set test`, `--set train`). |
| Out of memory | `--workers 1`. |
| A job failed | Its log is in `work/logs/<job>.log`; re-run the command to continue. |
